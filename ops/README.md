# ZorHire database on the VPS

Since December 2026 the ZorHire database runs in a Postgres container on the same Hostinger VPS
as the backend, instead of on Neon. Neon's free plan suspended the database in November 2026
after hitting its monthly compute cap. The database is small (about 40 MB; resumes live in
Cloudflare R2), so a container is enough and costs nothing extra.

| Piece | Where |
|---|---|
| Postgres 17 + pgvector | `postgres` service in `docker-compose.yml` (profile `localdb`, data volume `postgres_data`, no public port) |
| Nightly backup | `db-backup` service, runs at 02:30 IST; keeps 7 dumps in `/opt/zortech/backups` and 30 days in R2 under `db-backups/<db>/` |
| Migration | `ops/migrate-neon-to-local.sh` |
| Undo migration | `ops/rollback-to-neon.sh` |
| Restore a backup | `ops/db-restore.sh` |

All of these can be run from GitHub without SSH: **Actions → VPS database ops → Run workflow**
(this works once `.github/workflows/vps-db-ops.yml` is on `main`).

## Migration day (1 December 2026, when Neon's quota resets)

1. Merge this PR to `main`.
2. Run the workflow with **preflight**. It prints the VPS's CPU, RAM and disk, and checks that Neon
   is reachable. It changes nothing. It stops with an error if there is less than 600 MB of free RAM
   or 5 GB of disk; in that case, use Neon's paid Launch plan instead.
3. Run the workflow with **migrate**. It:
   - adds `POSTGRES_PASSWORD` and `COMPOSE_PROFILES=localdb` to `/opt/zortech/.env`;
   - starts Postgres and stops the backend so nothing writes during the copy;
   - dumps Neon (main DB and, if `LEDGER_DATABASE_URL` is set, the ledger DB) and restores the dumps locally;
   - compares the row count of every table between Neon and the copy;
   - only if all counts match, points `SERVER_DATABASE_URL` / `LEDGER_DATABASE_URL` at the container, starts
     everything and waits for `/v1/health`;
   - takes the first backup.

   If any step fails, it puts the old `.env` back and restarts the backend on Neon.
4. Run the workflow with **status** to see the containers and the first backup.
5. Log in to ZorHire and check jobs, candidates and the pipeline.

Neon is never modified. Keep the Neon project for a couple of weeks as a fallback, then delete it.

## Everyday operations

- **Backup now:** workflow action **backup-now**.
- **Check backups:** workflow action **status**. It shows the last run time and exit status.
- **Restore** (on the VPS): `bash /opt/zortech/ops/db-restore.sh` lists the backups;
  `bash /opt/zortech/ops/db-restore.sh r2:db-backups/zorhire/zorhire-YYYYMMDD-HHMM.dump` restores one.
  The current database is saved first, so a restore can itself be undone.
- **Back to Neon:** workflow action **rollback**. Data written after the migration is not copied back.

## Settings (`/opt/zortech/.env`)

| Key | Default | Meaning |
|---|---|---|
| `POSTGRES_PASSWORD` | generated by the migration | Password for the `zorhire` DB user |
| `COMPOSE_PROFILES` | `localdb` after migration | Turns the postgres and db-backup services on |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` | same as resume storage | Where backups are uploaded. Without them, backups stay on the VPS only. |
| `DB_BACKUP_R2_BUCKET` | `R2_BUCKET` | Use a separate bucket for backups |
| `DB_BACKUP_TIME` | `02:30` | Daily backup time (IST) |
| `DB_BACKUP_KEEP_DAYS` | `30` | Days of backups kept in R2 |
| `DB_BACKUP_LOCAL_KEEP` | `7` | Backups kept on the VPS, per database |

## Moving to a managed database later

If AWS Activate credits arrive or the data outgrows the VPS, take a backup and restore it into
RDS (or any Postgres 17 with pgvector) with `pg_restore --no-owner --no-acl`, then change
`SERVER_DATABASE_URL`. The app only needs the connection string.
